# Architecture notes

These notes explain *why* the code is shaped the way it is. They're meant for whoever reads or
extends the project next.

## Layering (modular monolith)

```text
FinSight.Api ──► FinSight.Application ──► FinSight.Infrastructure ──► FinSight.Domain
     │                                                                  ▲
     └──────────────────────────────────────────────────────────────────┘
```

| Project | Responsibility | Depends on |
|---------|----------------|------------|
| **Domain** | Entities (`LoanApplication`, `RuleAssessment`) and pure business rules (`EmiCalculator`, `LoanRuleEvaluator`). No framework references. | nothing |
| **Infrastructure** | `FinSightDbContext`, Fluent API mappings, migrations, seed data. Later: HTTP clients for IFSC and the LLM. | Domain |
| **Application** | DTOs (the API contract), validation attributes, services that orchestrate a use case (load → apply rules → persist). | Domain, Infrastructure |
| **Api** | HTTP concerns only: routing, model binding, status codes, CORS, error handling, configuration. | Application |

This is plain layering, not full Clean/Onion architecture. Application uses the EF Core
`DbContext` directly instead of going through repository interfaces. `DbContext` already *is* a
unit of work plus repositories, and wrapping it would add code without adding value at this size.
The part that most needs isolation, the lending rules, is already isolated in Domain, so it is
unit-tested with no database or web host.

## Key decisions

**Money is `decimal` everywhere** (C# `decimal`, SQL `decimal(18,2)`). Binary floating point
can't represent 0.1 exactly, and EMI involves raising numbers to the 360th power, so errors compound.
`Math.Pow` only accepts `double`, so `EmiCalculator` uses its own exponentiation by squaring in `decimal`.

**Rounding happens once, at the end, half away from zero.** .NET's default is banker's rounding
(1.125 → 1.12). The currency convention is 1.13, and a test pins this behaviour.

**Intake validation is not the same as product rules.**
- *Structural* validation (DTO attributes, database check constraints) rejects impossible data:
  negative amounts, 0-month tenure, more than 2 decimal places. These requests get a `400`.
- *Product rules* (`LendingProductRules`: min/max amount, tenure, DTI…) are policy, and policy changes.
  An out-of-policy application is still stored, and the assessment flags it for a human.
  Rejecting it at the door would hide it from reviewers.

**Missing data is allowed and flagged.** Income, existing debt and employment type are nullable.
The evaluator never guesses: missing debt means DTI is `null`, not "assume 0".

**The rule engine returns flags, never a decision.** Each flag has a stable `Code`, a `Severity`
(Info / Warning / Critical) and a plain-English `Message` with the actual numbers. Approve/Reject
statuses exist only for a human to set. The same principle will apply to the AI layer.

**Assessments are append-only.** Each `POST /assess` inserts a new `RuleAssessment` row. This
keeps an audit trail of how flags changed as the data or rules changed. The FK uses `Restrict`
rather than `Cascade`, so deleting an application can't silently erase that history.

**Flags are stored as JSON** (`FlagsJson`, enforced with `ISJSON()`) instead of a child table.
They're always read and written as a whole and never queried individually yet. A child table can
be introduced if per-flag reporting is needed.

**Enums are stored as strings** (`"Salaried"`, `"UnderReview"`), so the data stays readable in SQL
and reordering the C# enum can't corrupt existing rows.

**Seeding uses EF Core's `UseSeeding`/`UseAsyncSeeding`** rather than `HasData`. `HasData` copies
every row into migration files and requires fixed values for everything. `UseSeeding` runs after
`dotnet ef database update`, is idempotent and keeps the demo data in one readable file.

**Secrets never touch the repo.** The connection string comes from user secrets (Development) or
the `ConnectionStrings__FinSightDb` environment variable. The app fails fast at startup with
instructions if it's missing.

**Errors are ProblemDetails (RFC 7807).** `[ApiController]` produces 400s with per-field errors.
`GlobalExceptionHandler` maps an unreachable database to `503` and everything else to a generic `500`,
logging full details server-side only.

**Dependencies are deliberately few:** no AutoMapper (mapping is a few explicit lines), no
FluentValidation (DataAnnotations plus one custom attribute covers it), and Swagger UI only
(the OpenAPI document is built into ASP.NET Core). One transitive package
(`System.Security.Cryptography.Pkcs`) is pinned to patch known CVEs.

## Database schema (current)

See [schema-InitialCreate.sql](schema-InitialCreate.sql) for the exact DDL generated by the migration.

- `LoanApplications`: PK, `decimal(18,2)` money, `decimal(5,2)` rate, 5 check constraints,
  index `(Status, CreatedAt)` for the dashboard's filter-and-sort query.
- `RuleAssessments`: FK → `LoanApplications` (`NO ACTION`), `ISJSON` check, index
  `(ApplicationId, CreatedAt)` for "latest assessment" lookups (also serves as the FK index).

`AIAnalyses`, `ApiUsageLogs` and `AuditLogs` are intentionally not created yet. They arrive with
the features that use them.
